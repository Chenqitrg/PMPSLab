## 1. Purpose of this document

This document records the design discussion, architectural decisions, implemented
work, unresolved review findings, and recommended next steps from the current
development session. It is intended to let another engineer continue the work
without reconstructing the reasoning from the commit history or chat transcript.

The project started this session as a periodic-MPS numerical codebase. The main
line of work became:

1. make long-running site-sweep algorithms cooperatively pausable and resumable;
2. make that execution model reusable by future algorithms, including outer
   LoopTNR RG loops;
3. reduce the memory and asymptotic cost of transfer products by introducing a
   factored, truncated representation;
4. harden the data model and cache protocols before enabling truncated execution
   in the production split algorithm.

The execution framework and checkpoint format now exist. Truncated transfer
products and direct factored split-environment consumers also exist. Two major
correctness findings from the architecture review have been fixed. The next
recommended change is to close the cache update protocol so callers cannot
silently create stale environments.

## 2. Executive status

### Completed

- A generic step-based execution interface exists for resumable algorithms.
- `PeriodicSplit` runs through that interface and stops only at completed-site
  boundaries.
- A local Julia REPL adapter supports cooperative pause, resume, and cancel.
- Split snapshots exclude derived caches and can reconstruct a run at the exact
  next iterator position.
- Snapshots can be stored as versioned JLD2 checkpoint files using an atomic
  publish-by-rename pattern.
- Directional periodic caches have been separated into left and right storage.
- Dense and truncated transfer matrices are separate representations.
- Truncated periodic products and cache multiplication are implemented without
  first materializing dense rank-4 products.
- Split environments can consume truncated BB and AB environments directly.
- Sweep domains are validated against the actual approximation size.
- `PeriodicMPS` now preserves its closed-bond invariant across construction,
  `setindex!`, and `copyto!`.
- Large transfer, split, and canonicalization tests have been separated into
  smaller files.
- The MPS and transfer-matrix source files have been split into directories by
  responsibility.
- The full test suite passed at the handover baseline.

### Not completed

- The raw cache transition protocol is still public enough to misuse. Correctness
  depends on hidden ordered-update assumptions.
- The exact empty-product identity is represented as a full-rank
  `TruncatedTransferMatrix`, which defeats the requested truncation budget and
  mixes identity semantics with approximation metadata.
- Krylov non-convergence is only warned about; it does not prevent a site update
  from being committed.
- `PeriodicSplit` still constructs dense caches. There is no user-facing cache
  representation/truncation option yet.
- Short-pause versus durable/long-pause lifecycle policy is not orchestrated.
- Cancel-with-checkpoint is not implemented.
- There is no platform adapter. This is intentional: the hosting platform is
  expected to own general job dispatch, resource allocation, and frontend APIs.
- There is no global Esc or Ctrl-C key binding. The REPL interface currently uses
  explicit Julia commands such as `pause!(session)`.
- Nested resumable execution for a future outer LoopTNR RG loop is designed for,
  but not yet implemented.

### Development chronology

The session progressed through the following stages. The ordering matters because
later decisions deliberately replace some earlier sketches.

1. **Baseline review and architecture cleanup.** The branch was reviewed against
   `origin/main`, followed by a broader architecture and test-coverage inspection.
   Early work completed the `PeriodicMPS`/MPSKit-facing API, generalized physical
   contractions, repaired split cost/log semantics, hardened solver integration,
   and expanded numerical regression tests.
2. **Pause/resume requirements elicitation.** The safe-point, durability, memory,
   cancellation, single-worker, frontend-progress, REPL, and future LoopTNR needs
   were clarified before introducing execution types.
3. **Generic execution skeleton.** The blocking split loop was decomposed into a
   reusable run protocol, a split-specific run/context, site events, and a local
   task-based adapter. Multiple small revisions clarified why iterator state is
   explicit and why the cursor does not belong in the context.
4. **Snapshot and checkpoint implementation.** Snapshot ownership was made
   explicit, cache reconstruction was added, restore was tested at sweep turns and
   wraps, and JLD2 disk persistence was introduced after checking its practical
   file/IO usage.
5. **Memory-oriented cache refactor.** Directional cache storage was separated and
   fixed-state containers were made immutable. The design assumes stable bond
   spaces so cache/tensor storage can be reused in place when compatible.
6. **LoopTNR/ALS research detour.** Parallel DMRG, LoopTNR, and ALS ideas were
   discussed. A research plan was written, then explicitly set aside so the main
   execution line could continue.
7. **Transfer representation refactor.** Dense, truncated, and periodic transfer
   concepts were separated; constructors were unified; factored multiplication,
   cache reuse, and direct split consumers were added; source and tests were split
   into focused directories.
8. **Architecture review and repairs.** A deliberately adversarial review produced
   findings R1-R6. R1 (sweep domain) and R2 (MPS closure under mutation) were fixed.
   The source layout was further cleaned by moving all MPS functionality under
   `src/mps/`.

## 3. Product and operational requirements captured in the discussion

The following requirements drove the execution design.

### 3.1 Pause semantics

- A pause request must not interrupt a tensor update halfway through.
- The current site is allowed to finish; the run becomes paused before the next
  site begins.
- A single site may take up to approximately one minute, so pause latency is at
  most the remaining duration of the current site.
- The frontend observes progress at site granularity. A site completion event is
  therefore both the numerical consistency boundary and the UI progress boundary.
- While a site is running, the state should be reported as "pause requested".
  Only after the site completes should it be reported as "paused".
- Algorithm parameters must not be mutated while a run is active or paused.

### 3.2 Resume and durability

- A disconnected client must not imply loss of the numerical run.
- A durable pause must write enough state to disk to resume later.
- Checkpoints should remain on disk indefinitely unless an explicit external
  cleanup action removes them.
- Resume should produce the same result as uninterrupted execution within machine
  precision.
- Derived caches need not be serialized if they can be deterministically rebuilt
  from authoritative state.
- The checkpoint must identify incompatible formats instead of attempting an
  unsafe best-effort restore.

### 3.3 Memory policy

- The target algorithms can have very large memory footprints, with important
  kernels scaling as badly as `O(D^6)`.
- A short pause may retain the live context and caches in memory for quick resume.
- A long pause should write a durable checkpoint and allow the live numerical
  context, especially derived caches, to be released.
- Julia garbage collection can reclaim unreachable tensors, but deterministic
  memory release requires dropping references. Checkpointing alone does not free
  the live run; the owner must also release it and may optionally call `GC.gc()`
  at an operational boundary.

### 3.4 Cancellation

- Cancellation is distinct from pause.
- The caller/frontend should be able to choose whether cancellation preserves a
  checkpoint.
- Current code only implements cooperative cancellation without automatic
  checkpointing.

### 3.5 Deployment boundary

- The code will eventually be embedded in a larger platform.
- The platform is expected to own general job assignment, user isolation, CPU and
  memory provisioning, request transport, and likely durable-object lifecycle.
- PMPSLab should own numerical state transitions, safe boundaries, snapshots,
  restore validation, and local control.
- The current deployment assumption is one user/job per worker allocation. A
  future multi-user platform is expected to isolate CPU cores and memory outside
  this package.

### 3.6 Generality

- Pause/resume must not be hard-coded to `PeriodicSplit`.
- Future algorithms may have different configuration types and completely
  different initial data.
- A future LoopTNR implementation should be able to pause both within an inner
  site sweep and between outer RG iterations.
- Julia's existing `AlgorithmContext` abstraction should be reused for mutable
  numerical working state, but it should not own generic scheduler/runtime state.

## 4. How the architecture evolved

### 4.1 From a blocking `split` call to explicit execution state

The original algorithm was naturally expressed as one blocking call. That made a
correct pause impossible: local variables, the iterator cursor, caches, and logs
were implicit in the stack frame.

The algorithm was therefore split into:

- immutable problem input and algorithm configuration;
- `SplitContext`, which owns mutable numerical working state;
- `SplitRun`, which owns execution progress and the next iterator tuple;
- `step!`, which completes exactly one safe algorithmic unit;
- `SplitSnapshot`, which captures durable authoritative state;
- `LocalRunSession`, which drives any `AbstractAlgorithmRun` and exposes local
  control commands.

The blocking `split` API remains as a convenience wrapper. It repeatedly calls
`step!` until `isfinished` and returns `run_result`, so the blocking and
controllable paths use the same numerical implementation.

### 4.2 Why the iterator tuple is stored

Julia's iteration protocol returns either `nothing` or `(value,
next_iterator_state)`. The second element is opaque and is not required to be
reconstructible from the yielded value.

For a sweep, the yielded value is a `SweepState`; it is not a general replacement
for the iterator's own state. Storing only the current site/direction could
duplicate or skip a boundary, a zigzag turn, or a sweep wrap after restoration.
`SplitRun.pending_iteration` therefore stores Julia's returned iterator tuple
directly, or `nothing` after exhaustion. The tuple is not wrapped in another
one-field type because that would add no invariant or behavior.

### 4.3 Why cache state is not in the snapshot

The MPS tensors and iterator position are authoritative. Transfer matrices and
prefix/suffix contraction caches are derived from those tensors. Serializing both
would introduce two copies of the same fact that could disagree.

A snapshot therefore stores:

- a deep copy of the current approximation `mpsB`;
- the exact pending iterator tuple;
- a detached copy of the split log.

On restore, the caller supplies the immutable target MPS and algorithm
configuration. `restore_run` validates the sweep and cursor, copies the saved
approximation, and rebuilds `SplitContext` and all derived caches.

### 4.4 Cache ownership and directional storage

The earlier cache layout forced left and right values into one array and mixed the
cache's numerical content with an active-site viewpoint. This was awkward for
in-place reuse and created multiple possible sources for the current site.

The cache now stores left and right directional arrays separately. The context is
site-independent, and the sweep cursor in `SplitRun` is the single source of
truth. Cache slots may be overwritten in place when tensor spaces permit it.

This refactor also reflects an important numerical property: bond spaces do not
change during the split sweep. Existing tensor storage can often be reused; the
old tensor becomes collectible after no live reference points to it.

### 4.5 From one transfer product implementation to explicit representations

Transfer matrices were made first-class representations because different
storage and multiplication strategies have materially different complexity:

- `DenseTransferMatrix` stores the exact eager transfer tensor.
- `TruncatedTransferMatrix` stores SVD-like factors `u`, `s`, and `vᴴ` plus a
  truncation strategy.
- `PeriodicTransferMatrix{T}` represents a periodic sequence whose element type
  is the concrete transfer representation.

The previously discussed name `SparseTransferMatrix` was rejected because the
representation is low-rank/truncated, not sparse in the usual index sense.

For two truncated factors, multiplication contracts only the retained factors,
performs an SVD on the smaller middle product, truncates, and absorbs the new
factors into the outer `u` and `vᴴ`. This is intended to replace direct `O(D^6)`
dense transfer multiplication with operations closer to `O(D^4)` when the
retained rank is small.

The consumer must support the factorized representation directly. Converting to
dense inside the sweep would erase the complexity benefit. Accordingly, the split
BB and AB environment contractions now have direct truncated methods.

### 4.6 Smaller design questions resolved along the way

Several smaller questions materially shaped the current code:

- **`AlgorithmProblem` versus algorithm type:** A universal struct bundling an
  algorithm with initial data was considered but not adopted. Algorithms have
  different input shapes and initialization rules, so Julia multiple dispatch on
  `initialize_run(inputs..., algorithm)` is the common abstraction. The platform
  may already have a generic job envelope; PMPSLab should not duplicate it.
- **`AlgorithmContext`:** It is useful, but only as the abstract home for
  algorithm-specific numerical working state. It is intentionally independent of
  a concrete algorithm and does not imply a single universal context layout.
- **Current versus next iterator state:** The yielded `SweepState` describes the
  work to do, while Julia's opaque iterator state describes how to continue. They
  are related but not interchangeable; neither is redundantly copied into
  `SplitContext`.
- **Timing:** `SiteLog.time` and `SplitLog.sweep_time` measure completed numerical
  site work. They are not pause timestamps and do not measure total session wall
  time. Pause duration belongs to an execution/platform lifecycle if it is needed
  later.
- **Copying:** Ordinary live tensor replacement should reuse storage where safe,
  but a snapshot must copy authoritative mutable values to guarantee isolation.
  These are different ownership requirements, not contradictory policies.
- **Mutable versus immutable structs:** Parametric/generic code does not require
  `mutable struct`. Mutability affects whether fields can be rebound, not whether
  a contained array or tensor can be mutated. The outer type should be mutable
  only when its fields represent changing state. Performance effects are secondary
  and workload-dependent; the primary reason is a truthful data model.
- **Gauge-fixing organization:** Empty or placeholder abstractions were not kept
  merely for symmetry. The active implementation now lives under
  `src/canonicalize/`, with projector construction separated from the public
  `gaugefix!` workflow.
- **Cache construction style:** `build_cache` was rewritten toward iterator/map
  and dispatch-oriented Julia code rather than manual representation-specific
  orchestration. This should remain subordinate to clear cache invariants; being
  syntactically "Julian" is not a substitute for an encoded transition protocol.
- **One-shot transfer products:** An extra class representing a temporary transfer
  product was rejected. `PeriodicTransferMatrix{T}` is sufficient to describe the
  sequence, while each concrete transfer type owns construction and multiplication.
- **JLD2 output boundary:** Checkpoint I/O is path-based. Investigation of JLD2
  usage supported using a seekable local file, followed by optional platform
  upload, rather than promising a generic arbitrary-`IO` streaming API that the
  format and backend do not reliably support.

## 5. Architecture Decision Record

The decisions below use the following statuses:

- **Accepted:** implemented or an agreed constraint for implementation.
- **Accepted, partial:** the architectural direction is implemented, but some
  lifecycle or integration work remains.
- **Deferred:** intentionally postponed.
- **Superseded:** discussed but replaced by a later decision.

### ADR-001: Use cooperative safe-point pausing

**Status:** Accepted  
**Decision:** A pause or cancellation request takes effect only after the current
site update completes.  
**Reason:** Tensor, cache, log, and cursor updates must form a consistent unit, and
the frontend already measures progress per site.  
**Consequence:** Pause latency can be up to one site duration. Hard interruption of
a numerical kernel is not supported.

### ADR-002: Represent execution as explicit algorithm runs

**Status:** Accepted  
**Decision:** Algorithms expose `initialize_run`, `step!`, `isfinished`,
`run_result`, `snapshot`, and `restore_run`.  
**Reason:** A Julia stack frame or `Task` is not a durable, portable algorithm
state. Different algorithms need different typed state while sharing the same
execution protocol.  
**Consequence:** Each future algorithm defines its own run and snapshot types.

### ADR-003: Keep runtime control outside algorithm state

**Status:** Accepted  
**Decision:** `Task`, `ReentrantLock`, callbacks/observers, and platform handles
belong to adapters such as `LocalRunSession`, never to snapshots.  
**Reason:** These values are process-local runtime mechanisms and cannot be safely
restored from disk.  
**Consequence:** Restoring creates a new runtime session around a reconstructed
algorithm run.

### ADR-004: Reuse `AlgorithmContext` for numerical working state

**Status:** Accepted  
**Decision:** Algorithm-specific contexts own mutable tensors, caches, and derived
quantities. Runs own configuration, cursor, and progress log.  
**Reason:** The existing abstraction fits numerical state, while pause control is
algorithm-independent and belongs one level above it.  
**Consequence:** `SplitContext` deliberately does not know the active site.

### ADR-005: Preserve Julia iterator state exactly

**Status:** Accepted  
**Decision:** Store the pending `(value, next_iterator_state)` returned by
`iterate`, or `nothing`.  
**Reason:** Julia does not guarantee that the next iterator state can be derived
from the current yielded value.  
**Consequence:** Custom sweep iterator state must be serializable if its run is to
be checkpointed.

### ADR-006: Snapshot authoritative state and rebuild derived caches

**Status:** Accepted  
**Decision:** Split snapshots contain the approximation, exact cursor, and log;
transfer products and caches are reconstructed on restore.  
**Reason:** This prevents duplicate sources of truth and makes long pauses release
cache memory.  
**Consequence:** Durable resume has a cache-rebuild cost but a smaller and more
robust checkpoint.

### ADR-007: Deep-copy snapshot-owned mutable data

**Status:** Accepted  
**Decision:** Snapshot tensors and log vectors are copied rather than aliased with
the live run.  
**Reason:** Continuing a run after taking a snapshot must not mutate the snapshot.
  
**Consequence:** Snapshot creation temporarily requires memory for another copy of
the authoritative tensors.

### ADR-008: Use JLD2 with an explicit compatibility header

**Status:** Accepted  
**Decision:** Checkpoints are JLD2 files with magic, schema version, algorithm tag,
and PMPSLab package version. They are supported only in the same PMPSLab and
dependency environment.  
**Reason:** TensorKit values already work with JLD2, and explicit metadata allows
early rejection of incompatible files.  
**Consequence:** Cross-version migration is not promised yet. A future schema
migration layer can be added when there is a real compatibility requirement.

The header fields have distinct purposes:

- **magic** (`"PMPSLab checkpoint"`) rejects unrelated or malformed files;
- **schema version** identifies the layout/meaning of the serialized payload;
- **algorithm tag** prevents interpreting one algorithm's snapshot as another's;
- **package version** currently enforces the strict same-version restore promise.

The JLD2 API is intentionally exposed through a filesystem path, not an arbitrary
`IO`. A platform may upload the completely written local file afterward.

### ADR-009: Publish checkpoints atomically

**Status:** Accepted  
**Decision:** Write a temporary file in the destination directory, close it, then
rename it to the final path.  
**Reason:** A crash or serialization failure should not expose a partially written
checkpoint as valid.  
**Consequence:** The destination directory must exist. Retention and remote upload
remain platform responsibilities.

### ADR-010: Distinguish short and long pauses

**Status:** Accepted, partial  
**Decision:** Short pause keeps the live run/context in memory. Long pause writes a
checkpoint, releases the live numerical state, and later rebuilds caches.  
**Reason:** Rebuilding caches for every brief interaction is wasteful, while
retaining an `O(D^6)`-scale context indefinitely is unacceptable.  
**Consequence:** The numerical primitives exist, but no policy currently decides
when a pause becomes long or drops the live run.

### ADR-011: Use commands, not global key interception, in the Julia REPL

**Status:** Accepted  
**Decision:** Local control uses `pause!(session)`, `resume!(session)`, and
`cancel!(session)`.  
**Reason:** Ctrl-C conventionally throws `InterruptException` into foreground
work, and Esc is owned by terminal/REPL editing. Neither provides a reliable
cooperative safe-point protocol.  
**Consequence:** A separate UI may map buttons or keys to these commands, but the
core package does not capture terminal keys.

### ADR-012: Keep the platform boundary narrow

**Status:** Accepted  
**Decision:** PMPSLab supplies step, event, snapshot, restore, and local-session
semantics. The host platform supplies scheduling, transport, job persistence
policy, and resource isolation.  
**Reason:** The platform already has supporting backend code, and coupling the
numerical package to an unknown job API would create speculative abstractions.  
**Consequence:** A thin platform adapter should be written only when its actual
interfaces are available.

### ADR-013: Split periodic caches by direction and keep the cursor in the run

**Status:** Accepted  
**Decision:** Store left and right cache sequences separately; do not duplicate the
active site in the cache/context.  
**Reason:** This improves in-place reuse and preserves a single source of truth for
execution position.  
**Consequence:** Cache transition ordering must be owned by the stepper; this is
the subject of pending review finding R3.

### ADR-014: Make containers immutable when field rebinding is not required

**Status:** Accepted  
**Decision:** Use immutable `struct` for fixed-shape configuration and state
containers; keep `mutable struct` only where fields themselves change, such as
`SplitRun` and `LocalRunSession`.  
**Reason:** Generic code does not require mutability. Immutable outer containers
better express invariants even when they contain mutable arrays or tensors.  
**Consequence:** Mutating contained numerical data remains possible; replacing a
field requires constructing a new outer value.

### ADR-015: Model transfer storage explicitly

**Status:** Accepted  
**Decision:** Use `DenseTransferMatrix`, `TruncatedTransferMatrix`, and
`PeriodicTransferMatrix{T}` rather than a temporary product wrapper or `isa`
branches in the sweep.  
**Reason:** Construction, multiplication, memory use, and consumer behavior differ
by representation and should be selected by dispatch.  
**Consequence:** New transfer representations must implement the small algebra and
the consumers they need.

### ADR-016: Treat site transfer construction as representation constructors

**Status:** Accepted  
**Decision:** One-site, two-site, and mixed bra/ket physical contractions are
constructors of the concrete transfer type.  
**Reason:** The representation should own how raw tensors become a transfer map.
This keeps physical contraction details out of periodic-product orchestration.  
**Consequence:** Dense and truncated types expose analogous construction paths.

### ADR-017: Truncated products must stay factorized end to end

**Status:** Accepted  
**Decision:** Truncated multiplication and split-environment consumption operate on
`u`, `s`, and `vᴴ` directly. Dense materialization is explicit and reserved for
reference/testing paths.  
**Reason:** Densifying before multiplication or solving restores the `O(D^6)` work
the representation was created to avoid.  
**Consequence:** Direct LU/Cholesky-style solvers are rejected for factored BB
environments; action-based Krylov solving is required there.

### ADR-018: Combine truncation policies with permissive OR semantics

**Status:** Accepted  
**Decision:** When factors with truncation policies are multiplied, the combined
policy permits truncation when either policy permits it, and should be simplified
to a direct strategy whenever possible.  
**Reason:** The intended policy is the more permissive truncation condition, not
the stricter intersection initially discussed. Avoiding nested policy trees also
prevents metadata growth across long products.  
**Consequence:** Error-based truncation is expected to be the primary practical
policy; slow singular-value decay naturally retains more rank.

### ADR-019: Cache reuse only needs the truncated middle space

**Status:** Accepted  
**Decision:** In the periodic-cache hot path, reuse checks compare the new `s`
space, not all outer `u` and `vᴴ` spaces.  
**Reason:** A cache slot denotes a fixed interval, bond spaces do not change, and
the interval endpoints define the outer spaces. Only the SVD-retained middle
space can change.  
**Consequence:** This assumption is valid inside the cache protocol. A general
public multiplication API would need a clearer precondition or broader checks.

### ADR-020: Do not truncate the mathematical empty-product identity

**Status:** Accepted direction, not implemented  
**Decision:** The cache boundary/empty product must remain an exact identity, but
it should not masquerade as an ordinary full-rank truncated transfer.  
**Reason:** Truncating it changes the algebra; storing it as an ordinary truncated
factor defeats the memory budget and makes `trunc` metadata misleading.  
**Consequence:** Introduce a lazy identity representation or encode an empty cache
boundary without an SVD factorization.

### ADR-021: Parallel LoopTNR acceleration is a research track, not the main line

**Status:** Deferred  
**Decision:** Do not immediately replace Gauss-Seidel-like sweeps with independent
Jacobi site updates. First measure the slow tail and test safeguarded nonlinear
acceleration such as Anderson/nonlinear GMRES/L-BFGS.  
**Reason:** Independent updates change convergence behavior and may not preserve
the fixed point dynamics. Existing observations suggest rapid early convergence
and a long slow tail: roughly `10^3` improvement in the first five of about forty
sweeps, then only another factor of ten.  
**Consequence:** The research plan is documented separately and should resume
after the execution/cache correctness line is stable.

### ADR-022: Numerical logs do not own pause accounting

**Status:** Accepted  
**Decision:** `SiteLog.time` is the duration of one completed site update, and
`SplitLog.sweep_time` is their accumulated compute time.  
**Reason:** These values support numerical performance/convergence analysis and
remain meaningful across pause/resume. Pause timestamps, queue time, and total
wall time are execution lifecycle concerns rather than properties of the split
algorithm.  
**Consequence:** `sweep_time` excludes time spent paused. A platform that needs
billing or UX timing must store its own lifecycle timestamps.

## 8. Architecture review findings and disposition

The detailed review is in `design/linus-style-code-review.md`.

| Finding | Severity | Current disposition | Required follow-up |
|---|---:|---|---|
| R1: sweep length detached from actual MPS | High | **Fixed** in `050c868` | A future breaking simplification may remove `N` from sweep configuration entirely, but silent mismatch is blocked now. |
| R2: public MPS writes can break ring closure | Medium-high | **Fixed** in `ea5288f` | Preserve pre-validation and atomic failed writes in future fast paths. |
| R3: cache correctness depends on hidden ordered transitions | Medium-high | **Open; next task** | Internalize unsafe cache transitions and make `step!` the owner of the legal sequence. Add stale-cache regression tests. |
| R4: truncated identity bypasses truncation policy | Medium | **Open** | Add a lazy exact identity/empty-boundary representation. Do not truncate identity. |
| R5: Krylov non-convergence is committed as success | Medium | **Open** | Return typed solver status and make site commit conditional on acceptance policy. |
| R6: callback contract in `SPEC.md` is stale | Low | **Open** | Update or remove the old callback promise; the current API uses execution events and session observers. |

### R1 fix details

`AbstractSweep` now has a `sweep_domain` contract. Built-in circular and zigzag
sweeps return `Base.OneTo(N)`. Fresh-run and restore paths validate this against
the actual approximation length before any update. Short, long, zero-sized, and
custom sweeps without a matching domain are rejected.

### R2 fix details

`PeriodicMPS` now validates closure even when constructed from an existing
`PeriodicVector`. `setindex!` validates the proposed tensor against both neighbors
before mutation. `copyto!` prepares and validates the complete replacement before
touching the destination, so a failure cannot leave partial changes. The one-site
period checks its own left and right spaces. Canonicalization was adjusted to
construct a fully validated result before copying it into the destination.

### R3 proposed closure

The preferred fix is deliberately small:

1. keep the cursor only in `SplitRun`;
2. rename raw ordered `advance!` to private `_advance!`;
3. rename the context-level raw `update!` to private `_update!` and stop exporting
   it;
4. make public `step!` the only operation that advances algorithm state;
5. keep `PeriodicCache` query-oriented from the public API;
6. rebuild a cache from its source product after any external bulk change;
7. add regression tests for out-of-order, repeated, and skipped cache updates, and
   tests that the unsafe operations are no longer part of the supported API.

This preserves the current high-performance cache representation without adding a
second cursor. Adding a cursor to the cache would violate the earlier single
source-of-truth decision.

## 9. Important current invariants

Future changes should preserve these contracts.

### Run invariants

- A successful `step!` returns only after tensor, cache, log, and cursor state form
  a consistent completed-site boundary.
- `isfinished(run)` means the pending iterator is `nothing`.
- `run_result` rejects unfinished runs.
- A snapshot remains unchanged if the live run continues.
- Restore validates both the sweep domain and the entire logged cursor history.
- Completion wins over pause/cancel requested during the final site.

### Context and cache invariants

- `SplitContext` owns numerical working state but no active-site cursor.
- `SplitRun` is the authoritative owner of the cursor.
- Cache intervals fix their outer virtual spaces because sweep updates do not
  change bond spaces.
- For truncated cache slot reuse, only the retained middle space is expected to
  vary.
- Cache correctness currently assumes legal, contiguous sweep transitions. Until
  R3 is closed, raw cache mutation must be treated as internal even though the API
  does not fully enforce that boundary.

### MPS invariants

- A `PeriodicMPS` is non-empty.
- Every tensor's right virtual space matches the next tensor's left virtual space,
  including closure from the final tensor to the first.
- Public mutation validates before writing.
- A failed `setindex!` or `copyto!` must leave the original object unchanged.

### Transfer invariants

- Dense transfer multiplication is exact.
- Truncated multiplication remains in factor form and applies its combined
  truncation strategy at the middle SVD.
- Explicit `dense(::TruncatedTransferMatrix)` is a reference/debug conversion, not
  an allowed shortcut in the performance-sensitive algorithm path.
- The exact empty product is mathematically an identity even when surrounding
  transfers are truncated.

## 10. Known limitations and risks

### 10.1 The safe boundary is only as atomic as the current implementation

`step!(::SplitRun)` currently calls `update!`, then appends the log and advances
the cursor. Inside `update!`, the tensor is written before all cache refreshes
finish. If a solver or cache operation throws after a partial mutation, the run is
failed but the in-memory context may not represent the previous safe boundary.

This does not corrupt an already published checkpoint, but it matters for retry
semantics. R5 should define a prepare/accept/commit boundary so an unaccepted
local solve never mutates the live MPS or cache.

### 10.2 Local task control is cooperative, not preemptive

On a multithreaded Julia process, `Threads.@spawn` lets the REPL remain responsive
while a site is running. On a single-threaded process, the async task yields only
after a completed site; a command can be handled between steps, not during a
CPU-bound site kernel. This matches the safe-point requirement but should be
explained in user-facing REPL examples.

### 10.3 A paused session still owns memory

`pause!(session)` changes control state only. It does not write a checkpoint,
drop `session.run`, or release caches. Long-pause orchestration needs a separate
owner because the current `LocalRunSession` type requires a live run.

### 10.4 Checkpoint compatibility is intentionally strict

The reader rejects a package-version mismatch. Dependency compatibility is stated
as a requirement but not fully encoded in the header. This is acceptable for the
current pre-1.0 workflow, but production retention across upgrades will require
either pinned environments or explicit schema migration tests.

### 10.5 Checkpoint lifetime is external

Files persist because PMPSLab does not delete them. There is no catalog, retention
policy, ownership metadata, storage quota, or garbage collection. The platform
must provide those capabilities.

### 10.6 Truncated execution is not yet wired into `PeriodicSplit`

Although the algebra and consumers exist, `SplitContext` currently calls dense
`PeriodicTransferMatrix` constructors. Enabling truncation before R4 and R5 would
make the incomplete identity and solver-failure semantics part of the main
algorithm path.

### 10.7 Exact associativity should not be assumed numerically

The discussion initially suggested truncated SVD multiplication might be strictly
associative because of SVD uniqueness. In finite precision, and especially with
rank/error truncation, grouping can change roundoff, retained subspaces near
degeneracy, and discarded information. The practical contract should be
approximate equivalence within a tested tolerance, not exact associativity.

### 10.8 Documentation drift

`design/resumable-execution.md` still uses some names that will become internal if
R3 is implemented. `SPEC.md` contains the stale callback design noted by R6.
Update both when the public boundary is finalized.

## 11. Recommended implementation plan

The order below is intended to protect correctness before exposing the new
performance path.

### Phase 1: Close the cache update protocol (R3)

**Goal:** Make it impossible for ordinary callers to issue a validly typed but
out-of-order cache update that silently returns a stale environment.

**Work:**

1. Inventory all uses of `advance!` and context `update!`.
2. Add the known four-site stale-cache counterexample as a regression test.
3. Decide which low-level methods remain module-private and rename them with `_`.
4. Remove raw update functions from `PMPSLab` exports.
5. Route all supported split progress through `step!`.
6. Add tests for repeated, reversed, and skipped update sequences at the supported
   API boundary.
7. Update `design/resumable-execution.md` to match the final names.

**Acceptance criteria:**

- The stale-cache counterexample cannot be expressed through supported public
  mutation APIs, or is rejected/rebuilt explicitly.
- No second active-site cursor is introduced.
- Existing split numerical tests and full `Pkg.test()` pass.

### Phase 2: Introduce an exact lazy identity (R4)

**Goal:** Represent an empty transfer product exactly without a full-rank SVD and
without pretending it obeys a truncation budget.

**Work:**

1. Add a small identity/empty-product representation to the periodic product
   algebra, or redesign boundary slots to encode emptiness.
2. Define left/right multiplication so identity returns the other factor without
   densification or truncation.
3. Remove the current construction that performs an exact full-rank SVD and then
   attaches the requested truncation strategy.
4. Test dense and truncated `N == 1` and boundary environments.
5. Add a regression proving `truncrank(1)` no longer allocates a bond-squared
   retained identity space merely to represent an empty product.

**Acceptance criteria:**

- Empty products are mathematically exact.
- No dense identity SVD is needed for truncated caches.
- Boundary queries remain type-stable and existing results remain within numerical
  tolerance.

### Phase 3: Make local solver outcomes explicit (R5)

**Goal:** Do not silently commit an unconverged Krylov iterate as a successful site.

**Work:**

1. Introduce a solver result carrying at least `value`, `converged`, residual, and
   solver information.
2. Define an algorithm policy for accept, retry, fallback, or fail.
3. Separate computing a candidate tensor from committing tensor/cache/log/cursor.
4. Extend `SiteLog` or the site event with solver status.
5. Ensure a rejected candidate leaves the previous safe state intact.
6. Test forced non-convergence and failure propagation through blocking split and
   `LocalRunSession`.

**Acceptance criteria:**

- No warning-only path advances the cursor after a rejected solve.
- `LOCAL_FAILED` exposes the underlying failure through the existing stored
  exception/backtrace mechanism or an improved public accessor.
- Successful dense paths retain current numerical behavior.

### Phase 4: Enable truncated split contexts

**Goal:** Let a `PeriodicSplit` configuration choose dense or truncated caches
without changing downstream algorithm code.

**Work:**

1. Add a representation/truncation configuration with a conservative default.
2. Construct BB and AB periodic transfers in the selected representation.
3. Require action-based Krylov solving when BB is truncated; reject incompatible
   direct solvers during initialization rather than mid-run.
4. Add end-to-end dense-versus-truncated accuracy tests for ordinary and graded
   spaces.
5. Benchmark time, peak memory, retained rank, and final cost over representative
   bond dimensions and error tolerances.

**Acceptance criteria:**

- The truncated main path never calls explicit `dense` on cache environments.
- Slow singular-value decay is allowed to retain rank rather than forcing an
  inaccurate approximation.
- Accuracy is controlled by the configured error policy and verified against a
  dense baseline.

### Phase 5: Complete durable pause/cancel lifecycle

**Goal:** Turn numerical checkpoint primitives into a complete local lifecycle
that a platform adapter can call.

**Work:**

1. Define a durable paused handle containing checkpoint location and minimal
   metadata, without retaining the live run.
2. Add a transition from `LOCAL_PAUSED` to durable pause: snapshot, write, verify,
   then release the live context.
3. Add restore/resume from a durable handle.
4. Add cancel policies: discard progress or checkpoint then cancel.
5. Decide whether an explicit `GC.gc()` is appropriate after releasing a very
   large run; keep it at the lifecycle boundary, not inside site kernels.
6. Test process restart, corrupted file, incompatible header, and failed write.

**Acceptance criteria:**

- A durable pause can survive a new Julia process.
- A failed checkpoint write does not discard the live safe state.
- Cancel-with-save publishes a valid checkpoint before reporting cancelled.
- Cancel-without-save does not delete older checkpoints unless explicitly asked.

### Phase 6: Add the real platform adapter

**Goal:** Connect the proven numerical lifecycle to the host platform without
moving platform concerns into PMPSLab core types.

**Work after platform interfaces are available:**

1. Map platform commands to pause/resume/cancel transitions.
2. Map `SplitSiteCompleted` events to frontend progress messages.
3. Store checkpoint identifiers/paths in the platform's job record.
4. Define ownership and cleanup for durable files.
5. Define recovery after worker loss and idempotency for repeated commands.

**Acceptance criteria:**

- The platform can show running, pause-requested, paused, completed, cancelled,
  and failed states without guessing from logs.
- Repeated or delayed requests do not duplicate steps.
- PMPSLab remains usable from a plain Julia REPL without the platform package.

### Phase 7: Add nested LoopTNR execution

**Goal:** Make an outer RG algorithm resumable both between RG iterations and
inside its current inner sweep.

**Suggested model:**

- an outer `LoopTNRRun` owns RG iteration state;
- the current inner algorithm run is explicit state, not a Julia `Task`;
- an outer snapshot contains the completed RG state plus an optional inner
  algorithm snapshot;
- safe boundaries include completed inner sites and completed RG iterations;
- the platform observes a hierarchical progress event with RG and site indices.

Do not implement this until the concrete LoopTNR state and platform needs are
known. The current generic interfaces were chosen to permit it without forcing a
single universal `AlgorithmProblem` struct.

### Phase 8: Resume acceleration research

Follow `design/looptnr-als-acceleration-research-plan.md`. Establish a serial,
exact baseline first; measure the slow tail; then compare safeguarded Anderson,
nonlinear GMRES, and L-BFGS-style acceleration by time to tolerance. Treat
parallel cache construction/update as a separate exact-parallelism optimization.

### Full tests

```julia
using Pkg

```

The full suite is relatively slow because TensorKit/graded-space compilation,
especially Z2 contraction paths, dominates startup. A typical full run during this

```bash
julia --project=. test/transfermatrix/runtests.jl

```

Execution and checkpoint tests are included by the root `test/runtests.jl` and can
also be targeted during development through Julia `include` in a test environment.

### Before each incremental commit

1. inspect `git diff` and keep unrelated user changes untouched;
2. run the smallest relevant focused tests;
3. run `Pkg.test()` for changes to shared representations, cache algebra, execution
   state, or MPS invariants;
4. run `git diff --check`;
5. commit only after the user has reviewed the increment and explicitly asked for
   a commit.

The user strongly prefers small, reviewable iterations. Avoid combining R3, R4,
R5, and main-path truncated integration in one change.

## 13. Practical REPL model

The intended current local use is conceptually:

```julia
run = initialize_run(target_mps, algorithm)
session = start_run(run)

pause!(session)          # becomes PAUSE_REQUESTED, then PAUSED after this site
run_status(session)
snapshot_state = snapshot(session.run)
write_checkpoint("split-checkpoint.jld2", snapshot_state)

resume!(session)
wait(session)
result = run_result(session)
```

For a process restart:

```julia
saved = read_checkpoint("split-checkpoint.jld2")
run = restore_run(saved, target_mps, algorithm)
session = start_run(run)
```

The target MPS and algorithm configuration are intentionally supplied again on
restore. They are immutable problem definition, not duplicated into the split
snapshot. Restore validates that the supplied sweep reproduces the saved history
and next cursor.

The example above is a low-level current model, not a final durable-session API.
In particular, accessing `session.run` and choosing checkpoint paths should be
wrapped by the Phase 5 lifecycle API before frontend integration.

## 14. Things not to do

- Do not serialize or attempt to restore Julia `Task`, locks, callbacks, or thread
  state.
- Do not interrupt a site kernel and call the partially mutated state paused.
- Do not store the same active-site cursor in both run and cache.
- Do not serialize derived cache state merely to avoid rebuilding it unless a
  measured restore bottleneck justifies a versioned cache optimization.
- Do not densify `TruncatedTransferMatrix` in the production split path.
- Do not truncate the exact empty-product identity.
- Do not assume an unconverged Krylov iterate is acceptable because it looks
  numerically plausible.
- Do not promise exact associativity of finite-precision truncated products.
- Do not bind Ctrl-C globally to cooperative pause in the numerical core.
- Do not invent a platform job abstraction before the platform interface is
  available.
- Do not enable truncated `PeriodicSplit` merely because its component tests pass;
  close R4 and R5 first.
